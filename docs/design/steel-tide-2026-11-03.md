## 0. 基座与硬约束

### 0.1 基础设定

| 项 | 决定 |
| --- | --- |
| 版本 / 加载器 | **Minecraft 1.21.1 + NeoForge ≥ 21.1.228**（开发基线 21.1.255） |
| 游玩场景 | 2–4 人小联机，核心全队唯一 |
| 技术路线 | 自研 Java 模组（状态机 / Tick / UI）+ Java config（驱动状态机的数字）+ KubeJS（配方 / 战利品 / 属性） |
| 失败惩罚 | 温和：核心归零 = 本波失败 + 待维修，**不拆建筑、不动库存** |
| 高阶门禁 | 配方全开，原料必须靠遗迹探索或怪潮产出 |
| 空中单位 | 首版改造原版幻翼，预留可替换接口 |
| 队伍机制 | 放置核心者为队长，队员通过核心 GUI 邀请，支持管理与转让 |
| **首版明确做 / 不做** | **做**：核心输出应力与转速（木头 16 RPM / 煤 64 RPM）；**不做**：应力的读取与显示（无应力表 HUD）、不响应机械动力的过载计算 |

### 0.2 技术分层与边界

**分层原则**：驱动状态机的数字进 Java config；内容定义（配方 / 战利品 / 标签 / 属性）留 KubeJS。判据是「谁在运行时读、读不到会怎样」，不是「改一次要不要重编译」。

| 层 | 内容 |
| --- | --- |
| 现成模组（不改源码） | Create(+Aeronautics)、TaCZ、TLM、结构类、JEI |
| **Java config**（`config/irontide/`） | 核心生命、燃料容量与速率、低功率阈值、模块 I/II/III 数值、波次表（Base / HeadMul / GearMul）、词缀表、维修天数、队伍上限、队长离线接管天数 —— **驱动状态机的数字** |
| **KubeJS** | 火药与弹药配方链、遗迹战利品表按 loot table id 注入、标签、Better Combat 的 `weapon_attributes` JSON、Ponder 思考场景 —— **内容定义** |
| **自研 Java** | 核心多方块识别、生命与燃料状态机、怪潮调度器、插件槽位、攻核 AI、组队与权限、战后结算 |

> **改数值改 `config/irontide/`，既不要动 Java 代码，也不要写进 KubeJS。** KubeJS 脚本抛异常只会打印一行红字然后作废，Java 侧随即静默使用默认值（燃料速率变 0、低功率惩罚永不触发），这类错误最难定位。config 能在载入时做范围校验，填错立刻报错。

## 1. 执行路线：客户端先行，再反推服务端

**策略依据**：单机模式 = 客户端 + 内置服务端跑在同一进程。BC / ParCool / GD656Killicon 这类双端模组在单机里自动生效，**不用先求联机服务端配合**。测完再机械地推导服务端该装什么——把"协商"变成"分类"。

### 1.1 阶段 A — 单机验手感（当前这一步）

只装：**最小基线 12 个 + 渲染三件套 + GD656Killicon + 近战手感 10 个**。
结构 / 地形 / 怪物 / 枪包 / 女仆附属 / DH **一个都别放**（世界生成类会污染归因，且必须开新档测）。

| # | 验收动作 | 判定 |
| --- | --- | --- |
| 1 | 光影开着挥一刀 | 第一人称**没有两把武器**（有 = Punchy Fix 没生效） |
| 2 | 一刀扫 3–4 只僵尸 | 每只都吃到伤害 → 决定 `config/bettercombat/server.json5` 横扫衰减关不关 |
| 3 | 持枪按 R / 按改过的键 | R 是换弹不是转刀；另一键出检视 |
| 4 | 造一台飞行器 + 女仆持枪打死僵尸 | 基线没被带崩 |

> **BC 换掉了整套攻击判定，"一只僵尸要几刀"的基准就变了。手感先定，数值后定** —— 否则先按原版攻击模型调完怪物血量，装 BC 后要全部重调。

### 1.2 阶段 B — 反推服务端

不要靠印象判断。用两处数据自动分三类：Modrinth 项目对象的 `client_side` / `server_side`，以及 jar 内 `META-INF/neoforge.mods.toml` 每条 dependency 的 `side`。产出见 **§4 双端差异表**。

**服务端 mods = 双端 + 服务端专属；纯客户端一个都别拷**（拷过去会启动失败或白占内存）。
其中 **BC、ParCool、GD656Killicon 三个必须版本逐字节一致** —— 它们有网络包 / 属性同步，服务端差一个小版本就会出现"客户端看着打到了、服务端判定没中"。

### 1.3 阶段 C — 2 人联机验收（才轮到求人装）

只测单机测不出来的四件事：BC 的服务端命中判定、ParCool 动作同步、Inspect 广播（gamerule `inspect_radius` / `send_inspections`）、Killicon 服务端记分。

### 1.4 阶段 D / E

- **D**：开新档测世界生成（结构 + SLO + Sparse + 地形），必须新档。
- **E**：上怪物 → 最后用 `config/irontide/` 调数值、用 KubeJS 调武器属性。

### 1.5 装机顺序

1. **最小基线 12 个**：NeoForge(≥21.1.228) + Create 6.0.10 + Sable 2.0.6 + Aeronautics 1.3.2 + TLM 1.5.3 + TaCZ 1.1.8-r7 + Pack Upgrader + KubeJS + Ponder + JEI + Jade + Sodium
2. **渲染三件套**：Iris + Flywheel Compat + **Iris Veil Compat**（用 BSL / Complementary 验航空学外观）
3. **GD656Killicon**：验僵尸图标 + 拿 TaCZ 的枪打出"精确命中"联动击杀类型
4. **近战手感四层**（10 个）：验 §1.1 的第 1–3 条
5. **性能层**：一次加完，Neruina / Chunky 别漏
6. **物流 + Create 附属**：**5 个一批**，每批测一次启动 + 一次产线满载
7. **怪物**：Hostile Skies 最先；装灾变顺带 Curios + Lionfish-API
8. **结构 + SLO + Sparse + 地形**：**开新档测**
9. 枪包、女仆附属、DH 放最后——都是"锦上添花但能炸掉基线"的类型
10. 版本锁死写进 `.agents/env.json` 的 `tools` / `paths`

> 所有版本号是 2026-11-03 的接口快照。下载前再按 Create `6.0.10` 锚点核一次附属适配版本——附属的 Files 页常把"支持 1.21.1"和"支持 Create 6.0.10"混着写。

## 2. 玩法设计（原样迁移，规则不变）

### 2.1 基地核心（T1 = 3×3×3 = 27 格）

**只用三种方块**，不做新贴图：

| 方块 | id | 数量 | 作用 |
| --- | --- | --- | --- |
| 安山机壳 | `create:andesite_casing` | 22 | 外壳，决定护甲与血量 |
| 十字齿轮箱 | `create:gearbox` | 4 | 中层四向接口，**应力输出口** |
| 安山核心 | `irontide:andesite_core` | 1 | 控制器，自研方块，不可替换 |

```
顶层 (y+1)   安山机壳 ×9
中层 (y)     四角安山机壳 ×4 ｜ 四向 = 十字齿轮箱 ×4 ｜ 中心 = 安山核心 ×1
底层 (y-1)   安山机壳 ×9
```

- **控制器坐标 = 结构锚点**，永远不动；后续所有档位只能向外长
- **模块不插进方块**：四个齿轮箱只承担“结构位 + 应力出口”，模块数据全部存在核心 BlockEntity，通过核心 GUI 安装/升级（不去改 Create 方块自己的数据）
- **结构校验时机**：方块放置 / 破坏 / 区块加载 / 服务器启动，外加 100 tick 兜底复查；**禁止每 tick 全量扫描**
- 结构不完整 → `INCOMPLETE`：停机、不耗燃料、不被攻打，**方块一个不掉**
- 玩家只能从外侧交互 → 核心状态必须支持**远距离查看**（HUD 或望远镜式 UI）

**外壳分级（按占比计算）**

| 材质 | id | 效果 |
| --- | --- | --- |
| 安山机壳 | `create:andesite_casing` | 基准：护甲 0、血量系数 1.0、效率 1.0 |
| 黄铜机壳 | `create:brass_casing` | 每替换一格：护甲、血量、燃烧效率按占比线性提升 |

- `实际值 = 基准 + (黄铜格数 / 外壳总格数) × 增量`，允许混搭，可以“先换一半”
- 机壳护甲走**固定减伤 + 硬上限**，与装甲模块的百分比减伤**乘算**叠加，禁止相加破 100%
- 全部数值进 `config/irontide/core.json`，不写死在代码里
- 方块 id 只通过 `create:` 命名空间读取（可扩展 `create:copper_casing`、`create:railway_casing`），**不碰 Create 内部 API 取外壳信息**

- 未装燃料模块时：容量 12,000、效率 150%（应急惩罚态）
- 核心基础生命 **500**

### 2.2.1 档位与升档（蓝图驱动）

固定 T1，其余档由**玩家自建 + 蓝图**决定形状：

| 档 | 边长上限 | 最大格数 | 形状来源 |
| --- | --- | --- | --- |
| T1 | 3 | 27 | 内置 pattern（§2.1） |
| T2 | 5 | 125 | 玩家自建 + 蓝图 |
| T3 | 7 | 343 | 玩家自建 + 蓝图 |
| T4 | 9 | 729 | 玩家自建 + 蓝图（上限） |

**升档流程（T2 起）**

1. 玩家手工围出更大结构，**必须包含原核心坐标**
2. 手持「结构记录器」右键两个对角 → 蓝图存进**物品 NBT**（不落文件、不依赖 Create 的 `.nbt` 蓝图格式）
3. 蓝图 + 材料放进核心 → 校验：边长 ≤ 当前允许档、包含原控制器、外壳只在白名单材质内、结构连通、目标格可替换
4. 通过 → 逐格建造，**每 tick 放 3 格**（125 格 2 秒 / 343 格 6 秒 / 729 格 12 秒），材料从核心库存扣
5. 血量**按百分比保留**（旧 80% → 新 80%）

**安全规则**：只往空气/可替换方块上放；碰到非白名单方块立即中止并报坐标，**绝不覆盖玩家已有建筑**。

**大档位的额外收益**：模块等级上限抬高（T1 封顶 III）+ 新增槽位类型（T2 起）。

### 2.3 燃料系统

- **接受任何原版熔炉可燃烧的物品**，燃烧值沿用 vanilla fuel registry
- **消耗速率**：5 点燃烧值 / 秒 ≈ 6,000 点 / 游戏日（约 3.75 块煤 / 天）
- **低功率阈值**：燃料 < 15% → **先降速到 16 RPM / 256 SU**、预警降级、信标模块失效、奖励 −50%；**燃料耗尽才归零**
- 燃料应由机械动力产线自动化供给（伐木→木炭，或种植→木炭 / 煤炭洗选）

### 2.3.1 应力输出（核心 = 前期唯一动力源）

| 燃料 | 转速 | 应力容量 | Create 里的参照 |
| --- | --- | --- | --- |
| 木头（原木 / 木板 / 木棍） | 16 RPM | 256 SU | 大水车量级 |
| 木炭 / 煤炭 | 64 RPM | 1024 SU | 一级蒸汽引擎量级 |

- 输出档位由**当前正在燃烧的物品**决定；换燃料需等当前燃料烧完，或在核心 GUI 手动清空
- 应力从中层四个十字齿轮箱朝外输出，能接几根轴由传输模块等级决定（§2.2）
- Create 为**软依赖**：Create 不存在时核心照常运行，只是不输出应力
- **配方安全线（防死锁）**：火药产线的最小可用燃料必须能徒手获得（原木 / 挖到的煤）；**禁止**要求“先用产线做出木炭才能发电”

### 2.4 怪潮系统（10 天周期）

**时间轴**

| 天 | 事件 |
| --- | --- |
| 第 8 天 | **预警**：广播本波规模与组成（完整度取决于信标模块等级） |
| 第 9 天 | **侦察**：揭示完整威胁组合与词缀列表；**干预**：消耗物资削弱 / 替换一个词缀（每波限一次） |
| 第 10 天夜 | **进攻**：刷怪，持续到被清空或天亮 |

**怪潮不可取消。**

**强度公式**：`最终规模 = round( Base(N) × HeadMul(P) × GearMul )`

| 波次 | 怪物总数 | 词缀数 | 词缀最高等级 |
| --- | --- | --- | --- |
| 1 | 14 | 1 | I |
| 2 | 20 | 1 | I |
| 3 | 26 | 2 | I |
| 4 | 32 | 2 | II |
| 5 | 38 | 2 | II |
| 6 | 44 | 3 | II |
| 7 | 50 | 3 | III |
| 8+ | 56（封顶） | 3 | III |

- **HeadMul(P)** = 1 + 0.35 × (P − 1)，P = 参与本波的在线人数（1→1.00，2→1.35，3→1.70，4→2.05）
- **GearMul** = 1 + 0.25 × (核心等级 − 1) / (最大核心等级 − 1)，**上限 1.25**
- 关键：GearMul 上限只有 +25%，而 Base 从 14 涨到 56（×4）。动态缩放只做"防碾压"兜底，保证玩家升级仍有净收益感
- **目标分配**：攻核 / 攻玩家比例随波次从 30 / 70 过渡到 50 / 50

### 2.5 攻核路径（两条并行）

**地面单位**：正常寻路，只能破坏**白名单方块**

- 可破坏：泥土、沙子、砂砾、原木、木板、树叶、玻璃、干草块、羊毛、藤蔓、竹子、普通陶瓦
- 不可破坏：石头及衍生、深板岩、金属类、所有机械动力方块、所有模组机器、黑曜石、核心结构方块
- → 设计压力：**木结构会被拆，石 / 金属结构安全**

**空中单位**：无视地形，直飞核心上方俯冲攻击，不破坏任何方块

- **首版实现**：改造原版幻翼 —— 攻击目标改为核心、取消"不眠症"刷新条件、由怪潮调度器主动刷出、只对核心造成伤害。**不引入新实体、不做新模型**
- **接口预留**（后续换成任意飞行实体时无需改动调度器）：

```java
public interface ICoreAirRaider {
    /** 由调度器在刷出时注入本次的目标核心 */
    void setRaidTarget(BlockPos corePos, ResourceKey<Level> dim);
    /** 巡航/俯冲/攻击由实体自行实现 */
    void tickCoreRaid();
}
```

```js
// KubeJS 侧：本波可用的空中单位表，Java 不硬编码任何具体实体
coreRaid.airRaiders = [
  'minecraft:phantom',       // 首版唯一
  // 'aeronautics:airship',  // 后续接入示例
]
```

调度器在刷怪阶段读这张表 roll 出空中单位 → 刷出 → 判断是否实现 `ICoreAirRaider` → 注入目标。换型式 = 改一行配置 + 写一个实体。
> 现成替代来源见 §3.9 的 Create: Hostile Skies（可驾驶的 Sable 飞艇），但它是很新的模组，必须单独验过再并入。

| 遮蔽 | 第 8 天预警只给规模不给组成，侦察费用 ×1.5 |

### 2.7 奖励与维修

| 组成 | 说明 |
| --- | --- |
| 基础掉落 | 怪物正常掉落 + 通用货币「怪潮残骸」 |
| 词缀战利品 | 每个词缀对应一种稀有材料（如「空袭」→ 航空学核心部件） |
| 防守表现 | 核心剩余生命 ≥90% → 残骸 +50%；≥50% → +25%；<50% → 无额外 |

**维修**：消耗「核心维修套件」×1 + 等待 1 个游戏日。维修期间无预警、无奖励加成；下一波仍会来临（不可跳过）。

### 2.8 探索与门禁

- **载体**：结构类模组 + KubeJS 注入自定义战利品表，不自写结构
- **门禁形式**：配方全部开放，但高阶合金、枪械改件、航空学核心的原料只能来自遗迹与怪潮
- 首版只做**一处遗迹**的战利品注入

### 2.9 火药与弹药产线

- 基础火药：建立最小动力网络后即可量产（Create 自动化：硝石 / 硫磺 / 木炭 路线）
- 基础弹种：完全自动化
- 高阶弹种：需要遗迹部件或怪潮战利品作为原料

### 2.10 东方小女仆定位

- **长期定位**：战斗向 + 生产辅助（农场 / 搬运 / 战场清理）**两者都要**
- **首版只做战斗向**：持枪参与守核心，见效快、验证成本低
- 生产向留到后续版本

### 2.11 组队系统（Java 实现）

核心不放建立队伍数据的地方，放**核心方块自身携带** —— 每个核心有唯一 Team 归属，队长由放置者承担。

**角色定义**

| 角色 | 数量 | 产生方式 |
| --- | --- | --- |
| **队长（Owner）** | 1 | 放置并激活核心的玩家，自动成为队长 |
| **管理员（Officer）** | 0–N | 队长任命 |
| **队员（Member）** | 上限可在 config 配，默认 **4 人** | 接受邀请或申请通过后加入 |
| **待处理（Pending）** | 临时 | 已发出邀请尚未响应，或已提交申请尚未审批 |

**核心界面内的队伍页**：邀请（在线下拉 / 离线手输）、申请列表（通过 / 拒绝 / 全清）、成员列表（头像 / 角色 / 在线状态 / 最后在线时间）、管理操作（升降 / 踢出 / 退出 / 转让）。所有动作二次确认，队长任命 / 转让额外确认。

**权限矩阵**

| 操作 | 队长 | 管理员 | 队员 | 非队员 |
| --- | :---: | :---: | :---: | :---: |
| 查看核心状态（血/燃料/词缀） | ✅ | ✅ | ✅ | 只读（不可操作） |
| 放入 / 取出燃料 | ✅ | ✅ | ✅ | ❌ |
| 安装 / 升级 / 拆卸模块方块 | ✅ | ✅ | ❌ | ❌ |
| 执行词缀干预（消耗资源） | ✅ | ✅ | ❌ | ❌ |
| 发起维修 | ✅ | ✅ | ❌ | ❌ |
| 邀请成员 / 审批申请 | ✅ | ✅ | ❌ | ❌（只能提交申请） |
| 任命 / 罢免管理员 | ✅ | ❌ | ❌ | ❌ |
| 踢出成员 | ✅ | ✅ | ❌ | ❌ |
| 领取奖励 / 开启战利品 | ✅ | ✅ | ✅ | ❌ |
| **转让队长** | ✅ | ❌ | ❌ | ❌ |
| **解散队伍** | ✅ | ❌ | ❌ | ❌ |

设计要点：**日常协作权限给到管理员**，但改写归属的操作（转让、解散）严格锁定为队长唯一 —— 避免队长离线时管理员把队拆了。

**转让与离线处理**

- 转让：只能转让给**已在队内的成员**；执行后原队长自动降为管理员
- 离线继承：队长连续离线超过可配置天数（默认 **7 个游戏日**，写在 config）→ 首版简化为**管理员可直接接管**，不做投票 UI
- 队长退出 / 被踢：不允许直接退出，必须先转让
- 解散队伍：队长确认后解散，但**不删除世界里的核心建筑**；核心转为「无主」，任何玩家可右键重新认领（原成员需重新加入）

**数据存储与同步**

- 队伍数据挂 **`SavedData`**（世界级），按核心方块坐标 / 核心 UUID 索引，随世界存档持久化，不依赖玩家登录状态
- 队长 UI 与成员列表通过自定义 **network packet** 同步给开了核心 UI 的客户端
- 玩家加入队伍后，HUD 显示队友状态（在线 / 生命 / 距核心方位），便于怪潮时分工
- **必须同时实现 command 兜底**：`/core team invite|accept|leave|promote|kick|transfer|disband|info`

**规则边界**

- 队伍**跨维度共享**：谁在下界或末地都不影响从属关系
- 核心本波失败（生命归零）**不影响队伍结构**，只影响奖励与核心状态
- 一人多核心：**首版不支持**（一个账号在一个世界内同时只能归属一个队伍），这条写死，避免数据模型复杂化

**KubeJS**

1. 火药与弹药配方
3. 遗迹战利品表注入
4. 稀有材料与维修套件物品定义
5. **Better Combat 的 `weapon_attributes` JSON**（自研武器、女仆武器、怪潮掉落武器）

### 2.14 战利品注入策略（通用）

1. **不要在 KubeJS 里逐个列举战利品箱**：用 loot modifier 按 **loot table id 规则统一注入**
2. 只挑 1–2 类箱子挂玩家自定义表（例如筛 YUNG's dungeon / Structures Arise 的表 id），其余保持原样，避免遗迹变成"物资超市"
3. 掉落物在 KubeJS 里定义为**一组「回收部件」物品**，不掉原版高级装备，保证所有收益都流回 Core 循环
4. 掉落权重与每组抽取数量写成常量，方便试玩后调速

### 2.15 性能约定

- **不要在 KubeJS 里写每 tick 遍历区块的逻辑**
- 结构模组数量直接等价于世界生成开销；先用最小集验证开图与探索不卡，再逐步加
- 首版必测两件事：① 第 10 天夜间刷怪峰值是否掉 TPS；② Create 产线满载 + 怪潮同屏的帧数。**这两项不达标，其余数值调优都没有意义**

## 7. 对外表述（原「思路稿-对外」核心内容）

**项目名**：钢潮 IRON TIDE（暂定，发布前定稿）

**一句话**：**每 10 天，怪物会主动来拆你的工厂。而你的工厂，既是它们的目标，也是你唯一活下来的理由。**

**要填的坑**：科技包缺外部压力（没有东西检验产线）、战斗包缺经济闭环（战斗不消耗造出来的东西）、枪械包缺后勤（弹药不是产线的产物）。钢潮补的就是这个缝 —— **让产线产出直接决定你能不能活过第 10 天**。

**三个记忆点**

1. **基地是一颗会死的心脏**：3×3×3 核心，有血条、要吃燃料、能装模块；但温和 —— 归零只判本波失败，不拆建筑不动库存。
2. **怪潮是可以谈判的**：第 9 天揭示完整词缀组合，可花资源削弱 / 替换一个，每波限一次。**是决策，不是背板。**
3. **木墙会被拆，铁墙不会**：攻核地面单位只能破坏白名单方块；空中单位无视地形直飞核心，逼你同时考虑防空。

**技术路线一句话**：驱动状态机的数字写进 Java config；配方、战利品、标签、属性这类内容写 KubeJS。

**核心循环**：探索遗迹 → 回收稀有部件 → 回基地搭产线 → 第 8 天预警 / 第 9 天侦察+干预 / 第 10 天夜战 → 结算 → 更高阶防御。
