# 《钢铁潮汐》是怎么做出来的

一份写给「想自己搭一个带自研模组的整合包」的人的实录。

不是设计文档（那个在 `steel-tide-2026-11-03.md`），是**动手顺序 + 踩坑记录**。你照着能复现同样的路，也能少走我走过的弯路。

---

## 0. 先看清这个项目由什么组成

《钢铁潮汐》不是「装一堆模组就能玩」的整合包。它是三层：

```
┌─────────────────────────────────────────┐
│  整合包层                                │
│  mods/ + config/ + kubejs/ + 任务书       │  别人下载后玩的东西
├─────────────────────────────────────────┤
│  自研模组 irontide                        │  这个仓库里真正有代码的部分
│  核心多方块 / 燃料 / 模块 / 怪潮 / 结算    │
├─────────────────────────────────────────┤
│  地基模组                                 │  不写，但决定玩法骨架
│  Create 6（机械）· TaCZ（枪）· FTB（任务）│
└─────────────────────────────────────────┘
```

关键认知：**自研模组只做地基模组做不到的事**。

Create 能给你旋转动力、传送带、机械臂，你不需要重写。你要写的是「核心这台机器怎么吃燃料、怎么被怪打、怎么算战利品」这种**只有你这个整合包才有的规则**。

写代码之前先问：这件事 Create 的机器能做吗？KubeJS 能改吗？数据包能配吗？三个都不行，才写 Java。

## 1. 环境：先让一个空模组能编译

这一步最容易卡住，卡住的原因几乎都是**下载不下来**。

### 1.1 你需要什么

| 组件 | 版本 | 说明 |
|---|---|---|
| JDK | 21 | NeoForge 1.21.1 强制要求 |
| Gradle | 9.x | 用 ModDevGradle 插件自带 |
| NeoForge | 21.1.265 | `neo_version` |
| ModDevGradle | 2.0.143 | `net.neoforged.moddev` |

### 1.2 第一次构建要联网，而且可能失败

NeoForge 的构建流程需要下载 `neoform-runtime`（反编译 Minecraft 用），从 `maven.neoforged.net` 拉。

**这个仓库在本机可能完全不可达**（curl 20 秒超时，`http_code 000`），表现为构建卡死在 `:createMinecraftArtifacts` 任务上，等十分钟也不动。

两个解法：

**A. 找一份已缓存的 Gradle home 复用**

```bash
GRADLE_USER_HOME="C:/Users/<你>/AppData/Roaming/modmind/gradle-runtime/cache" ./gradlew build --offline
```

只要那个 cache 里已经有 `neoform-runtime-2.0.24-all.jar`，离线就能构建。

**B. 挂代理后跑一次 `./gradlew build`**

只要成功过一次，产物会缓存在 `modules/irontide/build/moddev/artifacts/neoforge-21.1.265-merged.jar`（约 40MB）。之后断网也能构建，因为不再需要下载。

> **查 API 用这个 merged jar，不要靠记忆。**
> `javap -p -cp neoforge-21.1.265-merged.jar net.minecraft.world.item.ItemStack`
> 我在这个项目里被「凭印象写 API」坑了至少三次（见 §5.1）。

### 1.3 目录结构约定

```
mod_l61phe/
├── mods/                     第三方 jar（.gitignore 排除，靠清单重下）
├── overrides/                发给玩家的配置：config/ kubejs/ shaderpacks/

│   ├── libs/                 编译用的第三方 jar（也排除）
│   └── src/main/
│       ├── java/dev/modmind/irontide/
│       └── resources/
│           ├── assets/irontide/     贴图、模型、语言文件
│           └── data/irontide/       配方、战利品、配置默认值
├── 文件/                     设计文档、教程、交接
│   ├── 设计/
│   ├── 教程/
```

## 2. 自研模组的骨架

### 2.1 入口类

NeoForge 用 `DeferredRegister` 注册一切。一个模块一个注册表：

```java
public class ModMindEntry {
    public static final DeferredRegister.Blocks BLOCKS =
            DeferredRegister.createBlocks(MOD_ID);
    public static final DeferredRegister.Items ITEMS =
            DeferredRegister.createItems(MOD_ID);
    public static final DeferredRegister<MenuType<?>> MENUS =
            DeferredRegister.create(Registries.MENU, MOD_ID);
    public static final DeferredRegister<BlockEntityType<?>> BLOCK_ENTITIES =
            DeferredRegister.create(Registries.BLOCK_ENTITY_TYPE, MOD_ID);

    public ModMindEntry(IEventBus modEventBus) {
        BLOCKS.register(modEventBus);
        ITEMS.register(modEventBus);
        MENUS.register(modEventBus);      // 这行漏了 → GUI 打开直接崩
        BLOCK_ENTITIES.register(modEventBus);
    }
}
```

**`MENUS.register(modEventBus)` 漏掉**是很典型的坑：编译通过，单人也可能不崩，但客户端打开界面时报 `MenuType not registered`。

### 2.2 配置：JSON + 热重载

设计上所有数值都写 JSON，代码只读不硬编码：

```
data/irontide/config_defaults/core.json     → 运行时复制到 config/irontide/core.json
data/irontide/config_defaults/raids.json
data/irontide/config_defaults/multiblocks/core_base_3.json
```

好处是调数值不用重新编译。一次构建 → 改 JSON → `/reload` → 看效果，循环从 90 秒压到 3 秒。

代价是要写一个能容忍缺字段的解析器。我的做法是每个字段都有默认值，`JsonSupport` 里统一兜底，缺什么用什么。

## 3. 核心多方块：最难的一块

### 3.1 结构定义用 JSON，三种字符

```json
{
  "id": "irontide:core_base_3",
  "allowRotation": true,
  "layers": [
    { "0": ["###", "###", "###"] },
    { "0": ["#C#", "G#G", "#G#"] },
    { "0": ["###", "###", "###"] }
  ]
}
```

`#` = 机壳，`C` = 核心，`G` = 齿轮箱，空格 = 必须空气。

三层的 3×3，核心在中层靠边中点，这样玩家从外面能右键到它。

### 3.2 让它四向都能搭

**问题**：结构不对称，玩家从另一个方向搭就识别不了。

**做法**：复用 `allowRotation` 字段（原本闲置），语义改为「绕控制器做 4 个 90° 等价布局」。

```java
private static final int ROTATION_STEPS = 4;

// (dx, dz) → (-dz, dx)，即绕 Y 轴顺时针转 90°
private static List<Cell> rotate(List<Cell> cells) {
    List<Cell> out = new ArrayList<>(cells.size());
    for (Cell c : cells) out.add(new Cell(-c.dz(), c.y(), c.dx(), c.ch()));
    return out;
}

private static List<List<Cell>> buildLayouts(List<Cell> base, boolean allowRotation) {
    if (!allowRotation) return List.of(base);
    List<List<Cell>> layouts = new ArrayList<>(ROTATION_STEPS);
    List<Cell> cur = base;
    for (int i = 0; i < ROTATION_STEPS; i++) {
        if (layouts.stream().anyMatch(l -> sameLayout(l, cur)))
            throw JsonSupport.invalid("旋转布局在转满 4 次前就重复了");
        layouts.add(cur);
        cur = rotate(cur);
    }
    return layouts;
}
```

那个「转 4 次必须回原样」的自检很值钱：转 90° 的公式写错一个符号（`(dx,dz)→(dz,dx)` 而不是 `(-dz,dx)`）时，人会看出来，但代码不会报错，只会默默给出错误的布局。自检直接拒绝加载。

### 3.3 校验：四套布局里挑最接近的

```java
public StructureCheckResult check(Level level, BlockPos anchor, MultiblockDefinition def, CoreConfig config) {
    StructureCheckResult best = null;
    for (int i = 0; i < def.layouts().size(); i++) {
        StructureCheckResult r = checkLayout(level, anchor, def, config, def.layouts().get(i), i);
        if (r.complete()) return r;                       // 一套命中就走
        if (best == null || r.missingCount() < best.missingCount()) best = r;
    }
    return best;                                          // 否则给缺得最少的那套
}
```

**为什么必须挑最少的**：玩家搭到一半右键，提示会告诉他「还差 3 格」。如果随便返回一套，可能说「还差 12 格」，玩家会以为整个搭错了。

### 3.4 一个坑：结构校验别用 `BlockState#is`

判断「这一格是不是机壳」时，不要写 `state.is(MyBlocks.SHELL.get())`。

Create 的机壳是带变体的（`axis`、`waterlogged` 之类），`is()` 对 Block 有效但对某些包装过的不一定。用 `state.getBlock() == expected` 更直接，也更省一次注册表查询。

## 4. GUI：从「能开」到「能看」

### 4.1 打开面板必须带 payload

第一版写的是：

```java
player.openMenu(new SimpleMenuProvider(
        (id, inv, p) -> new CoreMenu(id, inv, core), title));
```

单人游戏一右键就**掉线**，报：

```
java.lang.NullPointerException: Cannot invoke "FriendlyByteBuf.readBlockPos()" because "buf" is null
  at CoreMenu.<init>
  at IContainerFactory.create
```

**根因**：`Player#openMenu(MenuProvider)` 只发 `ClientboundOpenScreenPacket`（menuType + title），**不带 extra data**。客户端构造菜单时 `IContainerFactory.create(id, inv, buf)` 收到的是 `null`，而我的构造器第一行就 `buf.readBlockPos()`。

**修法**：用 `ServerPlayer` 的重载，把坐标写进 extra data：

```java
if (player instanceof ServerPlayer serverPlayer) {
    serverPlayer.openMenu(
        new SimpleMenuProvider(
            (id, inv, p) -> new CoreMenu(id, inv, core),
            Component.literal("钢铁潮汐 · 安山核心")),
        buf -> buf.writeBlockPos(pos));       // ← 关键这一行
    return InteractionResult.CONSUME;
}
```

同时客户端构造器加 `@Nullable` 判空兜底，防止别的路径再次传 null。

### 4.2 数据同步：ContainerData 现取现用

面板要显示血量/燃料，这些每秒都在变。别用字段缓存，用 `ContainerData` 代理：

```java
private static final class CoreData implements ContainerData {
    private final AndesiteCoreBlockEntity be;

    @Override public int get(int index) {
        return switch (index) {
            case DATA_HEALTH -> be.getStructureHealth();
            case DATA_FUEL -> be.getFuel();
            case DATA_POWER_STATUS -> be.getPowerStatus().ordinal();
            // ...
            default -> 0;
        };
    }
    @Override public void set(int index, int value) { /* 只读，空实现 */ }
    @Override public int getCount() { return DATA_SIZE; }
}
```

客户端用 `SimpleContainerData(DATA_SIZE)` 占位，服务端定期 `broadcastChanges()`，屏幕每帧读 `menu.getCarried()` 同款接口。

### 4.3 按钮反馈：原版按钮的「白光」不是 bug

用户报「点按钮后白光不消失，以为没按到」。

那个白光是 **MC 原生的 hover 高亮**，鼠标不移开就一直亮，跟点没点到无关。真问题是**点完没反馈**。

修法两颗药一起吃：

```java
button.setFocused(false);                    // 清焦点，白光立刻消失
this.feedback = "已重新校验结构";             // 再给一句文字
this.feedbackUntil = Util.getMillis() + 2200;
```

### 4.4 配色：别硬抄资源包

我一开始按某个 Create 风格资源包采样，做出深灰 + 木纹的一版，被用户直接否了。

后来定稿的是**暖色米黄**：

```java
int TITLE_BG   = 0xFF4C3426;   // 深棕标题带
int MAIN_BG    = 0xFFE6D6AC;   // 米黄主体
int ACCENT_LINE= 0xFFC08F55;   // 分隔线
int SLOT_FACE  = 0xFFD7C59D;   // 槽位面
int BAR_BG     = 0xFF8B7355;   // 进度条底
```

**纯色矩形自绘，不用任何 png**。`fill(x1,y1,x2,y2,color)` 画完，加一圈 1px 亮边就是「内凹」，加一圈暗边就是「外凸」。

好处是改色只改常量，不用重画贴图；坏处是做不出纹理质感。取舍看你要什么。

### 4.5 文字发糊：`drawString` 的最后一个参数

```java
guiGraphics.drawString(font, text, x, y, color, false);
//                                                ↑ shadow
```

传 `true` 会画一层偏移 1px 的暗色投影。在浅色背景上看起来就是「两层发糊」。**全部传 `false`**。

## 5. 那些让我停下半小时以上的坑

### 5.1 燃料值：1.21.1 的 API 和你想的不一样

我想当然写了 `level.fuelValues().getBurnTime(stack)`。

编译直接报「找不到符号」。查了才知道：

- `Level#fuelValues()` **是 1.21.2+ 的东西**，1.21.1 没有
- `Item` 类**没有** `getBurnTime` 方法
- 正确写法是 `ItemStack#getBurnTime(RecipeType.SMELTING)`，它走 NeoForge 的 `FURNACE_FUELS` datamap

```java
private static int burnTimeOf(ItemStack stack) {
    return Math.max(0, stack.getBurnTime(RecipeType.SMELTING));
}
```

> 教训：**1.21.1 和 1.21.2 的 API 差异比你想象的大**。版本号只差一个小版本，方法直接不存在。

### 5.2 存档容器：`ContainerHelper` 签名对不上

```java
ContainerHelper.saveAllItems(tag, container);        // ❌ 不存在
```

1.21.1 只有：

```java
saveAllItems(CompoundTag, NonNullList<ItemStack>, HolderLookup.Provider)
loadAllItems(CompoundTag, NonNullList<ItemStack>, HolderLookup.Provider)
```

要么自己转 `NonNullList`，要么**直接用 `SimpleContainer#createTag/fromTag`**：

```java
tag.put("fuelSlot", fuelSlot.createTag(registries));
fuelSlot.fromTag(tag.getList("fuelSlot", Tag.TAG_COMPOUND), registries);
```

后者省事得多，除非你需要和别的容器互操作。

### 5.3 KubeJS 1.21 没有 `genericLootTables`

想用 KubeJS 往 13 张战利品表里塞东西，写：

```js
ServerEvents.genericLootTables(event => { ... })     // ❌ Unknown event
```

KubeJS 2101.7.2 的 1092 个类里，loot 相关只剩一个 `LootDataTypeMixin`。这个事件在 1.21 **已经不存在**了（功能挪到独立的 LootJS 模组）。

**不加模组的做法：NeoForge GLM 纯 JSON 三层**

1. 建一个注入用的表 `data/irontide/loot_table/dungeon_inject.json`，里面按权重写掉落
2. 每张目标表建一个 modifier `data/irontide/loot_modifiers/<slug>.json`：
   ```json
   {
     "type": "neoforge:add_table",
     "conditions": [{"condition": "neoforge:loot_table_id", "loot_table_id": "minecraft:chests/simple_dungeon"}],
     "table": "irontide:dungeon_inject"
   }
   ```
3. 在 `data/neoforge/loot_modifiers/global_loot_modifiers.json` 里列出所有 modifier 的 id

干净、无依赖、可版本控制。

### 5.4 KubeJS 脚本会重复执行 → `redeclaration of var`

```js
const Foo = Java.loadClass('com.example.Foo')     // ❌ RuntimeError: redeclaration of var Foo
```

KubeJS 会在**同一个作用域**里把脚本跑两遍（一次扫描、一次执行）。任何顶层 `const`/`let` 第二遍就撞名。

三个应对，按推荐度排序：

```js
// ① 最好：什么都不声明，需要就用的时候内联取
let stack = Java.loadClass('com.example.Foo').create().build()

// ② 可以：挂到全局对象上（不会重复声明）
global.myFoo = global.myFoo || Java.loadClass('com.example.Foo')

// ③ 能用但脏：变量名加随机后缀（下次还是可能撞）
```

注意 `Java.loadClass('a.b.C')` **会把 `C` 绑进作用域**，所以下面这种写法一样撞：

```js
const C = Java.loadClass('a.b.C')     // ❌ C 已经存在了
```

### 5.5 Mixin 的 `defaultRequire: 1` 是核弹

装了一个 KubeJS 扩展模组，启动直接崩：

```
InvalidInjectionException: Critical injection failure:
@Inject annotation on renderText could not find any targets matching
'renderText(GuiGraphics, int, int, Font, String, boolean)V'
```

对方要注入的方法，在目标模组的新版本里签名变了（最后一个参数 `boolean` → `Component`）。因为 mods.toml 里 `defaultRequire: 1`，**一个注入点找不到就整个游戏起不来**。

> 判据：**装任何带 mixin 的桥接模组前，先看它的 mixin 目标在不在你的版本里**。
> 方法：`javap -p` 目标类，对比描述符。
> 另外，如果那个桥接模组提供的功能你自己用 20 行代码就能做到 —— 别装它。

### 5.6 光影三件套版本互相锁死

这是最阴的一组，三个模组各锁一个版本区间：

| 模组 | 必须 | 原因 |
|---|---|---|
| Sodium | **0.8.12**（不能 0.8.13） | Iris 1.8.14-beta.1 引用 `SodiumOptions$PerformanceSettings`，只有 0.8.12 有 |
| Iris | 1.8.14-beta.1 | 1.8.12 引用的是老版 `SodiumGameOptions`，0.8.x 已删 |
| irisveil | 0.4.0 | Create 6 带的 Veil 渲染后端需要桥到 Iris 管线 |
| Sodium Extra | **0.9.3**（不能 0.9.5） | 0.9.5 的依赖写死 `[0.8.13+mc1.21.1]`，上界锁死 |

而且 Veil 是通过 `sable`（Create 6 渲染后端）以 jarjar 内嵌进来的，`Mod veil only supports sodium 0.8.12+` 这条报错你得翻到 `sable-neoforge-*.jar` 里面才能理解。

> **捷径**：找一个「玩法和模组接近、光影正常工作」的整合包，看它的 mods 目录版本组合。我从别人的包里直接抄了上面这四行，省了两小时。
> 前提是那个包的 Create 大版本和你一致（6.x）。

### 5.7 第三方模组的 `neoforge.mods.toml` 版本号能让游戏起不来

```
java.lang.IllegalArgumentException: 3.1-1.21.1+: Empty pre-release
  at java.lang.module.ModuleDescriptor$Version.<init>
```

模组作者写了 `version = '3.1-1.21.1+'`。Java 的模块版本规范要求 `+` 后面必须是 build 段，空的就抛异常。

修法是拆 jar 改一行：

```python
import zipfile, shutil
src, dst = 'bad.jar', 'fixed.jar'
with zipfile.ZipFile(src) as zin, zipfile.ZipFile(dst, 'w', zipfile.ZIP_DEFLATED) as zout:
    for item in zin.infolist():
        data = zin.read(item.filename)
        if item.filename == 'META-INF/neoforge.mods.toml':
            data = data.replace(b"version = '3.1-1.21.1+'", b"version = '3.1-1.21.1'")
        zout.writestr(item, data)
```

### 5.8 两个模组抢同一批 mixin → 只能二选一

`punchy`（第一人称动画）和 `firstperson`（First Person Model）都混入 `ModelPartMixin` 和 `LivingEntityRendererMixin`。同时装必然手臂渲染错乱。

不是崩溃，是**渲染错乱**，更难查。

判断方法：拆 jar 看 mixin 配置里 `"target"` 或 `@Mixin` 的类名，重叠的就是冲突。

选一个留下，另一个改名成 `.jar.disabled`。改配置比删文件好，回退只要改回名字。

### 5.9 TaCZ 的「不在手上的枪」会在第一人称出现

现象：手持剑时，一把 AK 以巨大歪斜形态出现在视野里。

查了半天以为是第一人称渲染模组的锅，其实在 TaCZ 自己的配置里：

```toml
# config/tacz-client.toml
DisableThirdPersonOffhandAndHotbarGunRender = false   → 改成 true
```

TaCZ 会把非主手的枪当挂件渲染，那条路径在第一人称下没正确裁剪。

> 顺序很重要：**先翻配置文件，再怪代码**。TaCZ 的 config 里大半问题都有开关。

## 6. 构建与验证

### 6.1 一次构建

```bash
cd modules/irontide
GRADLE_USER_HOME="<有缓存的 gradle home>" ./gradlew build --offline
```

产物 `build/libs/irontide-0.1.0.jar`。

### 6.2 同步到两个地方

```bash
cp build/libs/irontide-0.1.0.jar ../../mods/modmind-local-irontide.jar
cp build/libs/irontide-0.1.0.jar ../../.modmind/minecraft/mods/modmind-local-irontide.jar
```

**两处都要**：`mods/` 是发版用的，`.modmind/minecraft/mods/` 是本地测试实例用的。只改一处就会出现「本地好好的，发出去没了」。

### 6.3 验证产物，不要验证退出码

Gradle 说 `BUILD SUCCESSFUL` 不等于 jar 里有你要的东西。每次都查：

```bash
unzip -l build/libs/irontide-0.1.0.jar | grep -E "你的新文件"
```

我漏过一次 `models/item/xxx.json` —— jar 构建成功，进游戏物品显示成**粉紫格子**（MC 的缺模型占位图）。贴图、lang、创建标签全对，就差那一个 108 字节的 JSON。

> 物品显示粉紫格子 = 缺 `models/item/<id>.json`，不是贴图坏了。

## 7. 分工建议

如果你也想做「整合包 + 自研模组」，我建议按这个顺序：

1. **先定玩法骨架，只装地基模组**，跑通一个世界
2. **写设计文档**，把数值（容量、消耗、伤害）全列出来 —— 写文档花的时间，会在调数值时十倍还回来
3. **自研模组只做核心那一台机器**，第一个版本只要能放、能校验、能显示状态
4. **数值全部走 JSON**，把「改一次编译一次」的循环打断
5. **再补外围**：模块、怪潮、结算、音效
6. **最后做整合包层**：任务书、战利品、光影、优化模组

反过来做（先堆模组再想玩法）会很难受，因为模组之间的版本冲突会吃掉你全部精力（见 §5.6，那一组锁死花了很久）。
